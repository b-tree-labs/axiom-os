# ADR-247: A person's verified facets resolve to one handle

**Status:** Accepted (2026-11-10)
**Related:** ADR-020 (federation identity and relationships), ADR-035 (human principal binding), ADR-041 (identity acquisition and verification), ADR-077 (local principal authentication, progressive trust), ADR-084 (identity unification: the actor context), ADR-103 (directory providers, group and membership resolution)

## Context

ADR-020 gives every principal one address, `@name:context`, and gives a person
a portable platform identity. ADR-084 resolves an `ActorContext` from the
credential checked at the identity boundary. Neither says what happens when one
person reaches a node through several credentials, and today each credential
becomes a different principal:

- a web sign-in becomes `@<subject>:<context>`, derived from the identity
  provider's subject;
- an API key becomes the principal it was issued to;
- the command line becomes the node owner recorded in the local identity file;
- a sign-in at a second site, through another identity provider, becomes yet
  another handle.

Each surface converts its own credential, so nothing joins them. Conversations
started in the browser are not visible from the command line. Memory written
under one handle is not recalled under another. A role or clearance has to be
granted to every handle separately and revoked from every one. An audit of
everything a person did is a manual join across spellings.

The conversions also go wrong independently. On 2026-11-10 the web chat used
the raw subject (an email address) as the principal, the tool authority turned
it into `@name@domain`, the handle grammar rejected that, and every tool call
on a node with a site policy was denied. That fix makes the chat agree with the
HTTP layer, but the handle it agrees on is still not the person's.

ADR-041 proposed verified owner bindings and unverified aliases for the node
owner at install time. It does not cover facets that arrive later, through the
web, through keys, or at another site.

## Decision

**A person has one record, holding a canonical handle and the verified facets
that resolve to it. The identity boundary resolves a facet to that handle; an
unlinked facet keeps today's derived handle.**

### D1 — The person record

The record holds the canonical handle (the ADR-020 platform identity, such as
`@name:home`) and a list of facets. A facet is one way of proving who you are:

| Kind | Identified by |
|---|---|
| Identity provider subject | issuer + subject (never the subject alone) |
| API key | key id |
| Node owner | node id + local account |
| Signing key | public key fingerprint |
| Email | address, with how it was verified |

Each facet carries who verified the link, when, and the assurance level of the
proof (ADR-084's `Assurance`). The record lives in the identity layer, beside
the principal registry, and is node-local unless federated by D5.

### D2 — Resolution happens once, at the identity boundary

`resolve_actor` looks the authenticated facet up. If it is linked, the actor's
handle is the person's canonical handle; if not, it is the derived handle used
today (`@<slug(subject)>:<context>` for a session). The `ActorContext` carries
both the handle and the facet that authenticated, so a receipt records the
person and the credential they used. Nothing downstream converts a credential
again: every surface reads the resolved handle.

### D3 — A link needs proof of both sides

A facet is linked only when one session proves both: the person is already
authenticated as the canonical handle, and then proves the new facet, by
signing in with the other provider, entering a code sent to the address, or
issuing the key from that session. An administrator may link on a person's
behalf, and the link log records that. Matching strings never links: two
providers asserting the same email address prove nothing about each other,
and an email claim counts only when its issuer is allow-listed and marks it
verified.

### D4 — History follows the link

Ownership, memory, grants and clearances key on the canonical handle. When a
facet is linked, whatever was owned under its derived handle is re-owned to
the canonical one in place (the `reown` the chat store gained on 2026-11-10),
and the move is logged. The person takes no step.

### D5 — Only the handle crosses federation

A peer sees the canonical handle and the assurance level, never the facets.
Which providers and keys a person uses stays on the node that verified them.

### D6 — Unlinking stops resolution and rewrites nothing

Removing a facet stops it resolving from that moment. Records made under it
keep the facet they were made with (provenance is immutable, ADR-027), and the
link log says whose they were. Revoking a person revokes every facet at once.

### D7 — An agent is not a facet

An agent acting for a person is a separate principal. ADR-035's accountable
human and delegation chain tie it to the person; linking an agent as a facet
would let it act with the person's own authority.

## Options considered

- **Keep per-surface conversions.** Lost: each surface is a separate chance to
  get the spelling wrong, and none of them can answer "is this the same
  person".
- **Use the email address as the identity.** Lost: a person has several
  addresses, addresses change and are reassigned, and ADR-020 already rejected
  email-shaped principals.
- **Merge facets into one `Principal`.** Lost: ADR-084 keeps `Principal` the
  minimal cryptographic identifier that capabilities sign over. A person record
  beside it composes; a bigger `Principal` would change every signature.
- **Rely on the directory (ADR-103).** Lost as the only mechanism: a directory
  answers membership within one organization, and the facets that most need
  joining come from different organizations' providers.

## Consequences

- A person granted a role or clearance once holds it through every surface,
  and revoking it once removes it everywhere.
- Conversations, memory and receipts follow the person across the web,
  the command line, keys and sites.
- `resolve_actor` gains one lookup per request, keyed by issuer and subject or
  key id; it must stay cheap and fail toward the derived handle, never toward
  another person's.
- Linking needs a small user flow (link this sign-in, link this key) and an
  administrator path, both of which write the link log.
- ADR-041's owner and alias bindings become two facet kinds in this record
  rather than a separate file.
