# ADR-244: Only the provisioning layer differs between providers

**Status:** Proposed (2026-11-09)
**Related:** ADR-170 (blue/green as infrastructure as code), ADR-182 (never down from our own causes), ADR-215 (a deployment has one size and every size sees the same cloud interfaces), ADR-219 (bronze as immutable objects), ADR-245 (a source changes its delivery path in six stages), ADR-246 (every infrastructure change passes one gate)

## Context

ADR-215 made the charts portable: a deployment has one size, and every size
sees the same names for disk, load balancing, secrets and object storage. It
says nothing about how those names come to exist on a given provider. Today
they exist in two ways. On a laptop and in CI, K3D supplies them. On every
real node, somebody provided them by hand.

That gap has three symptoms. A consumer that runs on an on-premises node
cannot show that the same code will run on a request-built VM cluster or on
a public cloud, because nothing but the charts is shared. A consumer repo
can grow its own chart and its own Terraform beside Axiom's, and then two
deployment definitions drift. And a node that was fixed by hand stays fixed
only on that node.

## Decision

**A deployment is three layers, and only the first may differ between
providers.**

*Figure: the three layers. Generated by `scripts/diagrams/infra_portability_diagrams.py`.*

1. **Provisioning** builds machines, network and storage, and writes one
   **standard inventory**: the cluster's API endpoint, the storage class
   `axiom-fast`, a `LoadBalancer` implementation, the External Secrets store
   `axiom`, and an S3 endpoint and bucket. There is one module per provider:
   K3D for laptops and CI, the on-premises node, request-built VMs running
   RKE2, and Terraform for GKE and EKS. A provider that hands out machines by
   ticket rather than by API records them in an inventory file, and the rest
   of the module runs from that file.
2. **The cluster base** (`axiom-cluster`) turns the inventory into the names
   ADR-215 defines. It is the same chart on every provider.
3. **The node** (`axiom-node`) with one site values file. It is the same chart
   on every provider, and the values file is the only per-site input.

Rules that keep it that way:

- **No provider API or SDK appears in a chart or in application code.** A
  provider is reached only through the inventory's names.
- **One deployment definition.** A consumer repo carries a values file and
  its content. It does not carry its own chart or provisioning code; where it
  does today, that is debt to retire, not a second definition to maintain.
- **One contract test.** It checks that the inventory's names exist and
  behave (a volume binds on `axiom-fast`, a `LoadBalancer` gets an address, a
  secret syncs, an object round-trips through the S3 endpoint). It must pass,
  together with the zero-gap upgrade test from ADR-182, on every provider
  before a deploy there counts.
- **Deploys pull.** Flux on the cluster pulls a release tag. Nothing pushes
  into a node, so a node behind a login with multi-factor authentication is
  deployed the same way as a cloud cluster.
- **A hand fix becomes code.** A change made on a node in an emergency becomes
  a provisioning default, a chart value or a contract-test check in the same
  change, so the next install cannot repeat the fault.

**Proof ladder.** Portability is shown in this order, each step on the same
two tests: K3D in CI; an on-premises node running entirely from the charts; a
request-built VM cluster; a short, spend-capped real apply on one public cloud;
the other public cloud by `terraform validate` and `plan` in CI until there is
a reason to pay for it.

## Options considered

- **Charts only, provisioning by hand per provider.** This is today. It lost
  because nothing proves that a hand-built cluster provides what the charts
  expect, and every new provider repeats the hand work.
- **One Terraform codebase for every provider, including ticket-provisioned
  VMs.** It lost because a provider that issues VMs by request has no API for
  Terraform to drive; forcing one in produces a module that pretends.
- **Provider-specific charts.** It lost because a chart per provider is a
  deployment definition per provider, which is the drift this ADR removes.
- **Crossplane or a cloud-agnostic control plane.** Viable later. It lost for
  now because it adds a platform to operate before the simpler contract has
  been proven on a single provider.

## Consequences

- Moving between providers is a provisioning module and a values file, and
  the contract test says whether the move worked.
- An on-premises node is the strongest evidence short of a cloud run, but
  only once all of its services run from the charts. Until then it proves the
  charts partly.
- Public clouds are checked by plan in CI at no cost; a real apply needs an
  approved spend cap and is torn down afterwards.
- A consumer repo that carries its own chart or Terraform has a retirement
  task, tracked in its own plan.
- Data leaves a provider over standard paths: S3 objects by sync, and Postgres
  through CloudNativePG backups.
