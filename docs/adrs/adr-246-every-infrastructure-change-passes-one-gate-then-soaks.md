# ADR-246: Every infrastructure change passes one gate, then soaks

**Status:** Proposed (2026-11-09)
**Related:** ADR-182 (never down from our own causes), ADR-197 (a switch is one runner with a gate, a lock budget, a soak and an explicit retire), ADR-238 (a person decides what reaches them), ADR-244 (only the provisioning layer differs between providers), ADR-245 (a source changes its delivery path in six stages)

## Context

A node already runs most of the checks that say whether it is healthy: a
daily delivery proof, a check that every service runs the installed release,
a nightly restore of the newest backup, and a frequent health probe of each
source. They run separately, report to different places, and some failures
reached nobody because no person was subscribed to them. Two things a healthy
node needs are not checked at all: that an expected source is still sending,
and that the real entry point answers.

ADR-197 gives every switch a gate built from declared probes. It does not say
which probes a node must pass before the next change starts, or how long a
change must run before it counts.

## Decision

**One command runs every node check, and no infrastructure change starts
until the previous one has passed it and soaked.**

![Diagram titled "Every infrastructure change passes one gate, then soaks". Eight checks run as one command: delivery proof, installed code, backup restore, source health, feed freshness, front door, headroom and alert delivery. They feed one gate that passes only when all pass. On pass, the change soaks for one day, 7 plus 7 days, or 14 days depending on its risk, and then the next change may start. On fail, the change rolls back or a person accepts a named exception.](../assets/diagrams/change-gate.png)

*Figure: the gate and the soak. Generated by `scripts/diagrams/infra_portability_diagrams.py`.*

| Check | Proves |
|---|---|
| Delivery proof | Everything delivered was read and reached gold, per source |
| Installed code | No service runs an older release than the one installed |
| Backup restore | The newest backup restores into a scratch database |
| Source health | Each source and its access respond |
| Feed freshness | Each expected source is still sending, not only that past files were read |
| Front door | Sign-in, the API and web assets answer through the real entry point |
| Headroom | Disk and database have room for the next step |
| Alert delivery | A failure reaches a named person (ADR-238) |

- **The gate is these checks registered as declared probes** in ADR-197's
  registry, so the switch runner, the deploy pipeline and a person at a
  terminal run the same set.
- **A failure means roll back or a named exception** that a person accepts in
  writing. An exception names the check, the reason and an expiry.
- **Soak by risk:** a routine release or configuration change runs one full
  daily cycle; a source's delivery-path switch (ADR-245) runs its overlap and
  fallback periods; a production database move runs 14 days.
- **Rehearsal is proportional.** One light rehearsal at the real risk; the
  gate, not the rehearsal, is the proof.

## Options considered

- **Keep the checks separate.** It lost because a separate check that reports
  nowhere is how failures went unseen for days.
- **Gate on deploy success.** It lost because a deploy can succeed while a
  service keeps running old code, a source has gone silent, or alerts reach
  no one.
- **A fixed soak for every change.** It lost because one day is too short for
  a source switch and too long for a configuration change.

## Consequences

- Alert delivery is itself a gate check, so a node with no subscribed person
  cannot pass.
- The two missing checks, feed freshness and the front door, must be built
  before the gate means what it says.
- Changes queue behind each other's soak, which slows a busy week and is the
  point.
