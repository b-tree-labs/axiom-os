## Overview

This is the master spec for one framework that today exists as parallel mechanisms: export-control gating, lane routing, serving-tier cost bounds, prompt hardening, tool authorization, purge, and audit. The framework's claim is that every interaction the platform performs, a chat turn, a tool call, a data query, an ingest, a memory write, an export, a purge, is the **same shape**: a request from an actor passes fixed **enforcement points** (PEPs), each consults one **decision engine** (PDP) that answers from **information providers** (PIPs) under versioned **policy sets** (regimes), and the answer is a permit or deny plus **obligations** that the enforcement point must discharge or deny, plus non-binding **advice**. Every decision leaves a **content-free record**. Content has a **lifecycle** that ends in verified destruction.

The vocabulary is XACML's (PEP, PDP, PIP, obligations, advice, deny-overrides, an error fails closed), chosen because those concepts survived even where that standard's machinery did not. Everything else about XACML (XML, remote decision calls, open-ended obligation identifiers) is deliberately not adopted.

The framework is assembled from what the platform already has. The 2026-10-05 asset survey (`scratchpad/framework/existing-assets-map.md`, to be archived with this spec) found the PDP already landed: GUARD's `decide()` (authz extension, `decide.py:93`) returns a typed `Verdict`, writes a receipt per call, and combines pluggable `PolicySource`s deny-first (`authz/policy.py:99`). This spec therefore **extends** GUARD and the existing seams; section "Reuse map" states, for every component, what is reused, what is added, and what must not be built twice.

## Vocabulary, reconciled

The survey found the framework's natural words already carry meanings in this codebase. The spec fixes the following usage; code and docs migrate toward it, and until they do, the qualified forms below are mandatory in new work.

| Word | Meaning in this spec | Existing collision and resolution |
|---|---|---|
| **Verdict** | GUARD's typed decision (`governance/verdict.py:104`), now carrying obligations and advice | None; this is the canonical type. |
| **Obligation** | A must-do action attached to a Verdict; the PEP denies if it cannot discharge it | `attest` "obligations" are recurring due logbook entries. Rename in prose to **logbook duties**; code name unchanged until a major version. |
| **Advice** | A non-binding hint on a Verdict, typically from a statistical PIP | Chat UI `Advice` strings are unrelated; qualify as **UI advice**. |
| **Policy set** | A versioned bundle of rules a `PolicySource` serves (a regime, site rules, budgets) | `src/axiom/policy/` is an NL directive store for classroom agents, not policy; `memory/policy.py PolicyCoord` is memory's four-scope config. Both keep their names; neither is "the policy engine". |
| **Regime** | A policy set for a regulated-data class (ADR-158) | New term, no collision. |
| **Lane** | A named processing path for a turn, with declared stage skips, graduated shadow to advisory to active | New term. The question-routing "route A/B" in consumer code is a two-lane special case. |
| **Guard / GUARD** | Only the authz decision engine | `agent_action_guard.py` and site-repo "guards" are PEPs; call them enforcement points. |
| **Intent** | GUARD's closed action verb (`governance/intent.py:22`) | RPE retrieval intents and routing-intent admissions are **retrieval intents**; the two classes named `IntentRegistry` must be disambiguated when touched. |
| **Hold** | A legal or retention hold that blocks purge (ADR-159) | `_hold_for_approval` is the approval queue; rename in prose to **approval hold**. |
| **Label** | A content marker with a source: detection, declaration, or inheritance (ADR-158) | Unifies `Classification` (4-tier), `RoutingTier` (2-tier), stored `access_tier`/`classification` strings, and federation `VisibilityHorizon`. These become label namespaces, not separate models. |
| **Tier** | Only prompt tiers T0 to T3 (ADR-160) | Model-capability tiers (ADR-054) become **model classes** in prose; medallion tiers keep their domain name. |

## Contracts

### C1. The decision call

Every PEP calls `decide(envelope, ctx) -> Verdict`. Additive changes, all optional so existing callers are untouched:

- `ActionEnvelope` (`governance/envelope.py:33`) gains optional fields: `labels` (the content labels in play, with their source kind), `regimes` (which policy sets apply), `cost` (estimated points and bytes per ADR-157), `harness` (the harness-profile id, generalizing the per-client EC flag), `lane` (the proposed lane). `to_dict()` stays content-free.
- `Verdict` gains `obligations: tuple[Obligation, ...]` and `advice: tuple[Advice, ...]`, both empty by default.
- Decision semantics follow XACML's four outcomes mapped onto the existing six-value `Decision` enum; an evaluation error or a missing attribute is **Indeterminate and fails closed** (maps to deny with reason).
- Combining is deny-overrides across all applicable policy sets, which is what `PolicySourceRegistry.combine` already does; "strictest handling wins" across regimes (ADR-158) is implemented as deny-overrides over handling obligations.

### C2. Obligations are a closed, versioned registry

The single lesson taken from XACML's failure: open-ended obligation identifiers destroy portability. The registry is code, each obligation has typed parameters, and a PEP that receives an obligation it does not implement **must deny** (the XACML discharge rule). Initial registry:

| Obligation | Parameters | Discharged by |
|---|---|---|
| `redact` | label or pattern set, replacement | result-side executors; precedent `memory/post_filter.py:147` |
| `store_nothing` | store classes (trace, memory, cache, analytics) | every write-side PEP |
| `store_content_free` | projection name | record stores; precedent `TELEMETRY_FIELDS` |
| `add_disclosure` | disclosure id from policy config | answer assembly; precedent the EC warning prepend (`gateway.py:2401`) |
| `verify_output` | verifier ids | post-generation PEP (ADR-160 verifiers) |
| `reshape` | max points, max bytes, method | serving PEP (ADR-157: downsample across the whole window) |
| `paginate` | cursor budget | serving PEP |
| `require_approval` | approver policy id | existing approval path (`ApprovalGate`, `_hold_for_approval`, RACI) |
| `require_stepup` | challenge | existing `Challenge` on Verdict |
| `rate_limit` | bucket id | bucket registry (`infra/ratelimit.py:316`); produces the so-far-unproduced `Decision.RATE_LIMIT` |
| `route_lane` | lane id | the lane runner |
| `purge_after` | retention class | lifecycle scheduler (ADR-159 triggers) |
| `record_decision` | record class | always implicitly present; see C5 |

Adding an obligation is a versioned change to this table and to at least one executor, with a conformance test proving the discharge rule (an unknown obligation denies).

### C3. PEP stages

The pipeline's named stages, each a PEP. For each: the existing seam it wires into, or the gap.

| Stage | Seam today | State |
|---|---|---|
| `route` | lane strategy runner (consumer shadow build; this spec lifts it) | to lift |
| `pre_retrieve` | RPE `build_plan` + routing-intent admission + `rag/gating.py` | landed, becomes a GUARD-consulting PEP; its chunk filter becomes a PIP |
| `post_retrieve` | chunk sanitizer (`rag/sanitizer.py`) | landed; add label inheritance |
| `pre_tool` | `tool.pre_invoke` on `HookBus` via `dispatch_tool` (`tool_gateway.py:82`) and `invoke_capability` | landed |
| `post_tool` | `tool.post_invoke` observers; MCP `gate_result_for_client` (`routing.py:579`) | partial: observers cannot modify; the result-modify seam must be added to `dispatch_tool` |
| `pre_generate` | `prompt.pre_submit` via `submit_prompt` (`prompt_gateway.py:45`) | **declared but unwired**; the gateway must route through it |
| `post_generate` | gateway `_scan_response`; chat `check_answer_provenance` | partial: finding-only today; becomes verifier executor (ADR-160) |
| `pre_answer` | answer assembly (citations, disclosures, envelope fields) | per surface |
| `write` | `CompositionService` for memory; **no PEP** for traces, caches, analytics | gap; `store_nothing` needs these |
| `egress` | vault `outbound_call` for credentialed calls only | partial; all processor egress must pass a PEP applying the regime processor rule |
| `ingest` | `screen_document` + `ingest_router.Disposition` | landed; detectors become PIP providers |
| `purge` | `ReaperRegistry` seed | to extend (ADR-159) |

Coverage is enforced the way authz already enforces it: the AST lint pattern (`authz/lint.py:141`) extends to "no stage handler without a decide call", and the exempt list is explicit, like `DIRECT_INVOKE_EXEMPT`.

### C4. PIP provider kinds

All providers use `ProviderBase` identity (uid, `config_hash`) so every decision can name the exact provider versions consulted.

- **Detectors** (deterministic lists and patterns; statistical; external). Deterministic ones decide; statistical and external ones only advise (ADR-152, ADR-158). External detectors never receive content unless the regime's processor rule allows it. Presidio-style PII detection is an optional external-of-core provider (MIT licence); Llama Guard class models cannot be bundled (licence) and would in any case be advisory. Existing: the EC term lists, `secret_scan`, `ec_screening`, the chunk sanitizer, `QueryRouter`'s chain.
- **Label sources**: detection (above), declaration (a matter, engagement, agreement or owner statement; new registry), inheritance (derived content carries its source's labels; wire into embedding, summary, cache and trace writes). `controlled_code`'s three-valued answer (controlled, not controlled, unknown) is the model: unknown is not clean.
- **Agreements**: the access-agreements registry (PRD; no code yet). Implemented as attest logbook entry types, not a new signing system; `rag/gating.build_principal_attestation` migrates onto it.
- **Identity**: `ActorContext`, webauth keys and sessions, MCP identity gate. Already landed.
- **Relationships**: the OpenFGA substrate seam (`authz/substrate.py:42`), as a PIP, never as the handling-rule engine.
- **Cost**: estimators per ADR-157 (window over native period times channels); token counters exist, inbound per-principal estimation is a gap.
- **Optional external PDP providers**: OPA or Cedar (both Apache-2.0) may serve a policy set behind `PolicySource`; the obligation registry remains ours, and the built-in engine remains the default and the fallback.

### C5. Decision records

Every Verdict writes a record. The record is **content-free by construction**: it reuses the `telemetry_projection` discipline (a fixed field list with a drift test) and `params_digest` hashing. New required fields: the policy-set versions and the T0 policy hash (ADR-160), the provider `config_hash`es consulted, obligations issued and their discharge status, label namespaces (never label evidence text). Records land in the existing GUARD receipt store and the signed attestation chain where the policy requires signing; whether a node key may sign machine decisions is an open question (attest posture currently says service principals never sign). Trace providers that accept full prompt and output (`TraceProvider.log_generation`) must gain a projection mode; under `store_nothing` they receive nothing.

### C6. Regimes and policy sets

A regime is versioned configuration (ADR-158): content classes, detector providers, agreements, handling rules, audit, retention, clocks. Loaded like `load_site_policy` (TOML, fail-closed on presence), registered as a `PolicySource`. The EC term lists become the first regime profile's lists and gain a version id (today they are mtime-reloaded, versionless). Request clocks (one month for an erasure response, extendable) reuse the attest duty scheduler pattern (`attest/obligations.py evaluate/tick`) renamed per the vocabulary table.

### C7. Lanes

A lane is data: name, stages it skips, toolset filter, policy it requires (`routing_core.LaneSpec` in the consumer shadow build, lifted here). Lane choice is a strategy provider (rules, trained classifier, composite, external) behind a registry; every choice is recorded with decider, confidence and disagreements; mode per lane is shadow, advisory or active, and only active skips anything. Guarded lanes act immediately because they only add protection. Graduation from shadow to active requires evidence and a decision. The graduation gate is itself a provider seam: the default is a human reading the lane report; a statistical graduation-gate product may be integrated behind the seam (one is approved for use, with the conflict-of-interest terms disclosed and recorded by the owner) and is never reimplemented here. Whatever gates, the decision, its evidence and its gate version land in the decision record.

### C8. Tools and harnesses

A tool's manifest declaration (AEOS `SkillSpec`) gains: data classes read and returned, side-effect class (read, write, destructive; `side_effects` exists), egress targets, cost class and output budget (ADR-157), required scopes and agreements. A tool without declarations is refused by the `pre_tool` PEP. Per-tool manifest hashes extend the existing aggregate `MCPSurface.content_hash`, so a changed description re-triggers approval (rug-pull defence). The toolset offered to a model is filtered by lane **before** any embedding-based tool selection runs (selection is itself attackable). Tool results enter prompts as T3 data (ADR-160). Harness profiles generalize `AXIOM_MCP_CLIENT_EC_CAPABLE` inside the existing `ToolSpec`/`client_capabilities()` matrix: a profile states locality, retention and training posture, and agreements held; the regime processor rule consumes it. External tool servers are processors, denied regulated content by default.

### C9a. The typed-decision engine (our own, local, calibrated)

Every place the framework consumes a statistical opinion is a **seat**: lane choice, detector advice, tool selection, retrieval triage, eval judging, alert triage, approval-risk scoring. Rather than a different model bolted into each seat, the platform ships one **typed-decision engine**, built by us, run locally, and consumed through three primitives:

- `judge(question, evidence) -> probability` (a yes/no with a calibrated probability),
- `choose(options, evidence) -> distribution` (a pick over a closed option set),
- `score(scale, evidence) -> level + distribution` (an ordinal rating).

Contract properties, each tested:

1. **Typed, closed outputs.** A decision names its seat, its option set and its evidence references. There is no free-text verdict to parse.
2. **Calibrated, and the calibration is a receipt.** Per seat and per deployment, stated confidence is continuously compared with graded outcomes, and the resulting reliability curve is published as a **calibration receipt** (stale, noisy and drifted states included). A seat whose calibration is unknown is treated as uncalibrated and its opinions carry no weight in graduation evidence.
3. **Local by default.** The engine runs on deployment infrastructure. It may only see content its regime rules allow, which is what lets it sit on paths a cloud classifier never can.
4. **Trained on our own labels.** Shadow records, disagreement records, human feedback events and graded outcomes are the training set; regulated content enters training only where the regime allows. Models are versioned artifacts with `config_hash` identity; a decision record names the model version that spoke.
5. **Advice until graduated.** An engine opinion is advice (C1) in every seat until that seat is graduated by evidence and a human decision, exactly like a lane. Deterministic rules remain the deciders for anything with legal weight (ADR-152).
6. **Confidence is never evidence.** A decision record carries the evidence references beside the probability; a high-confidence opinion with no evidence is just a guess with a number, and the record makes that visible.

The consumer-facing contract for providers behind this engine and behind the graduation gate is [spec-decision-providers](spec-decision-providers.md): seat registration, the typed-decision interface, the calibration receipt schema (live since its first deployment implementation), the standings API and the external-gate seam.

This subsystem is deliberately the market shape of the typed-decision products that appeared in 2025, built in-house because: it must run where the content is, it must be calibrated against our own outcomes rather than a vendor's benchmark, and its receipts must live in our record system. External typed-decision services remain possible as external PIP providers on unregulated content only.

### C9. Content lifecycle

Labels attach at ingest and by declaration; derived artifacts inherit them. Retention classes schedule `purge_after`. Holds block purge and are first-class records. Verified purge follows ADR-159: `PurgeProvider` extends the landed `ReaperRegistry` (`infra/tenancy.py:90`) with `verify_absent` and `residual`; the `UNREAPED` declared-honesty list becomes the unregistered-store report; `memory/lifecycle.Tombstone` gains a receipt reference; receipts are logbook entries in the signed chain; canary items prove the machinery can fail.

## Design

Execution order inside a PEP: build or amend the envelope, call `decide`, then on permit discharge every obligation before proceeding, failing closed on any it cannot discharge; on deny return the policy's refusal, which names the cheaper or permitted alternative where one exists (ADR-157). Obligation executors are registered per stage; an executor is pure where possible and records discharge in the decision record. Advice never changes control flow; it is recorded and may be shown.

Failure modes: PDP unreachable is Indeterminate, deny. A PIP timeout yields the attribute "unknown", and unknown is evaluated under the regime's rule (for labels: unknown is not clean). Receipt-store unavailable currently degrades silently in `decide()`; under this spec a regime may mark `record_decision` blocking, making the write part of the discharge.

Performance budget: route and pre-tool decisions add under 5 ms on permit (in-process sources, no network); detectors are bounded per stage; anything slower must be async advice, not a blocking decision.

Rollout: every new enforcement behavior ships shadow first (decide and record, do not enforce), then advisory, then active, per policy set and per stage, using the same graduation discipline as lanes. Existing behavior (EC path, serving gates) is migrated by re-expressing it as regime policy sets with byte-identical outcomes before any new enforcement turns on.

Conformance batteries, each with a negative control that proves the battery can fail: obligation discharge (unknown obligation denies), prompt-tier override attempts, tool poisoning and manifest drift, purge canaries, abusive-consumer cost battery (ADR-157), and store-nothing verification sweeps.

## Future-now commitments

The framework is specified for the operating environment that is arriving, not only the one deployed today. These commitments are binding on the design even where their first implementation is deferred, because retrofitting them is what this spec exists to avoid.

1. **Agents are the majority caller.** Decisions are made at machine speed and volume: the PDP stays in-process and microsecond-to-millisecond, records are written asynchronously unless a regime marks them blocking, and nothing on the permit path waits on a network.
2. **Authority arrives as a chain, not a principal.** The envelope carries the full delegation chain (human to agent to sub-agent to tool), authority only attenuates along it, and a decision can name the link that failed. The existing delegation spine and ADR-114 patterns are the seed.
3. **Everything federates.** Labels, regime profiles, decision records and purge travel between nodes: a purge propagates as signed tombstones along federation edges and the receipt states which peers acknowledged; a receipt is verifiable by a counterparty that trusts the chain, not the node. Vega's trust graph and the attest chain are the carriers.
4. **Streaming is the normal output mode.** Verifiers are classified as streamable (pattern absence checkable on a rolling window) or terminal (whole-answer checks); a regime declares which classes may stream and which hold until verified. "Hold until verified" is an obligation, not a surface habit.
5. **Policy is analyzable, not only testable.** Policy sets are expressible in a form that supports proof ("content labelled protected-health can never reach a processor without the named agreement"), with an SMT-capable engine (Cedar class) as the optional analysis provider. The conformance batteries remain the runtime check; analysis is the design-time one.
6. **Evidence is a product surface.** Decision records, calibration receipts, purge receipts and battery results compose into continuously generated evidence packs mapped to external frameworks (NIST AI RMF and its generative profile, ISO/IEC 42001, SOC 2 families), queryable by an auditor identity with aggregate-only rights. Compliance evidence is generated by operation, not assembled by hand after the fact.
7. **Metering is billing-grade.** Per-principal, per-seat, per-regime usage records are accurate enough to price, because future customers will be billed on them; the same records drive quotas today.
8. **Ephemeral by default is the direction.** New surfaces default to content-free records and store-nothing unless a declared need and regime permit otherwise; the write-side PEP makes that a property, not a review comment.

## Decisions

- ADR-152 fixed: statistical classifiers advise; lists, labels and agreements decide.
- ADR-157 fixed: the serving layer bounds cost; reshape over silent truncation.
- ADR-158 fixed: regimes are one mechanism; labels have three sources; processors default to denied.
- ADR-159 fixed: deletion ends in an independent verify and a signed, content-free receipt.
- ADR-160 fixed: the T0 prompt tier is platform-injected and hashed; enforcement is deterministic checks, not prompt text.
- ADR-114 fixed: authority rules are fail-closed site policy; this spec's regimes load the same way.
